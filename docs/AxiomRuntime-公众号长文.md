# AxiomRuntime：一条命令管住 Claude Code 和 Codex 的多 Provider 切换

如果你手上同时开着 Claude Code 和 Codex，并且用的是中转站而不是官方直连，下面这个场景应该不陌生：正在写代码，上游突然 502。要切到备用中转站，于是打开一个终端改环境变量，再打开另一个终端翻配置文件，改完发现其中一个还在往老地址发请求——因为某个全局凭证文件的优先级更高，把刚改的东西静默覆盖了。等排查完，思路已经断了。

这类事情的麻烦之处不在于难，而在于它反复发生，每次都要付出同样的成本，而且这个成本没有任何一方会帮你降下来：官方 CLI 不关心你在用哪个中转站，中转站不关心你在用哪个 CLI。所以中间需要有一层东西。

这一层已经有人在做了——如果你在用 cc-switch，那你已经知道这层的价值。这篇文章讲的是同一层的另一种做法：把它做成一条命令而不是一个桌面应用，并且让它不碰你的任何配置文件。第二节会详细对比两者的差别，包括 cc-switch 做得更好的地方。

---

## 一、先把问题说清楚：三个痛点，三个层次

同时用两个 CLI、在多个 API provider（中转站）之间切换，会遇到三个问题。它们的严重程度递增。

### 痛点一：配置分散，切换成本是乘法

两个 CLI 工具的配置机制没有任何交集。

Claude Code 认环境变量，要改 `ANTHROPIC_BASE_URL` 和 `ANTHROPIC_API_KEY`。Codex 不认环境变量，它认自己的配置文件——`config.toml` 里的 `model_provider`，加上 `auth.json` 里的凭证。而且全局 `auth.json` 的优先级更高，会静默覆盖你刚改的东西，排查起来毫无提示。

手动改的问题不只是慢，是容易改一半忘一半。改了 Claude 忘了 Codex，然后花很长时间排查为什么两边行为不一致。

更麻烦的是这个成本的增长方式：当你有三四个 provider 备用时，需要记住的操作组合是 provider 数量 × CLI 数量，是乘法而不是加法。

### 痛点二：不知道钱花在哪

中转站基本不给账单细节，本地也没有任何汇总。典型状态是：月底看余额突然少一大截，但完全不知道是哪个模型、哪个项目、哪次操作吃掉的。想优化都不知道从哪下手。

这是很典型的可观测性缺失——不是功能不够，是你看不见系统在干什么。

### 痛点三：人不在电脑前就干不了活

很多任务其实就一句话的事：改个配置、加个字段、跑一下测试看哪里挂了。但人在外面，只能等回去。

这不是效率问题，是能力的可达性问题。一个只能在特定物理位置使用的能力，实际价值会打折很多。

前两个痛点解决的是"用得顺不顺"，第三个解决的是"用不用得上"。

### 这三件事有一个共同点

它们看起来是三个独立的问题，但根子是同一个：**你缺一个统一的运行环境。**

- 配置分散，是因为没有一个地方统一持有"我现在用哪个 provider、哪个模型"这个事实。
- 不知道钱花在哪，是因为没有一个地方统一经过所有的模型请求。
- 人不在电脑前干不了活，是因为没有一个地方能接受来自电脑之外的指令。

所以这三个痛点不需要三个工具，需要一个中间层：它统一持有配置、统一经过流量、统一暴露入口。

## 二、它是什么

一句话定位：

> 一个统一的入口，管理你在多个 API provider 之间使用 Claude Code 和 Codex 的整个过程——包括路由、降级、用量、会话、诊断，以及从手机上远程执行。

两个前提得先说清楚：

**一，需要 Node.js 22.19 或更高。** Node 20 跑不了。如果 npm 报 `EBADENGINE`，别当普通警告忽略——那个状态下装出来的 CLI 是有问题的，先升 Node。

**二，它不装 Claude Code，也不装 Codex，不代发 token。** 它只管理你已经有的这些。`ai setup` 会检查这两个 CLI 在不在，缺了会问要不要装，但装的还是官方包。

### 2.1 第一次安装：四步

#### 第一步：确认环境

```bash
node --version    # 必须 >= 22.19.0
which ai          # 检查命令名有没有撞
```

`node --version` 如果低于 22.19，先升级。用 nvm 的话：

```bash
nvm install 22
nvm use 22
```

`which ai` 这一步别跳过。命令名就两个字母，撞名的概率不低——一些别名、一些 Python 工具、一些自己写的脚本都可能占用它。如果这一步有输出，说明已经有东西叫 `ai` 了，装完之后哪个生效取决于 `PATH` 顺序，会很难排查。

#### 第二步：安装

```bash
npm install --global @offerpilot/axiomruntime
ai --version
```

包名是 `@offerpilot/axiomruntime`，装完之后的命令是 `ai`。`ai --version` 有输出就说明装好了。

macOS 用 Homebrew 也可以：

```bash
brew tap linlangli/axiom https://gitlab.com/linlangli/axiom.git
brew install linlangli/axiom/axiomruntime
ai --version
```

Homebrew 装的是同一个 npm tarball，校验 SHA256 后放进隔离目录，并且固定用 Homebrew 的 `node@22`——所以不用管你系统里的 Node 是哪个版本。注意 tap 不在 GitHub，第一次 `brew tap` 必须带上后面那个 Git URL。

关于 root：全局安装可以用 root，但**运行 `ai`、Telegram 和常驻服务请用普通用户**。原因在 3.8 节。

#### 第三步：`ai setup`

```bash
ai setup
```

这一条命令做完所有初始化，四件事：

1. **创建配置目录** `~/.ai-gateway/` 和里面的状态文件。想换位置就设 `AI_GATEWAY_HOME` 环境变量。
2. **引导你添加第一个 Provider**——依次问名称、Base URL、API Key。
3. **验证这个 Provider**：测连通性 → 探测可用模型 → 设默认模型 → 分配优先级 `level: 1`。
4. **检查 Claude Code / Codex 在不在**，缺了问你要不要装。装的是官方 npm 包。

第三步值得说一下：模型名是探测出来的，不用你手输。手输模型名是这类工具最常见的出错点——名字差一个字符，上游就报 `model_not_found`，而错误信息通常不会告诉你是名字写错了。

如果你想跳过交互，或者在 CI、容器里初始化：

```bash
ai setup --yes --skip-tools       # 只做无交互的安全初始化，不装外部 CLI
ai setup --yes --install-tools    # 顺带安装缺失的 Claude Code / Codex
ai setup --skip-provider          # 跳过 Provider 引导，之后手动 ai add
```

`--yes` 不会自动授权安装第三方 CLI，必须显式加 `--install-tools`。缺少 Provider 凭证时它不会猜测或伪造，会直接告诉你缺什么。

#### 第四步：跑起来

```bash
ai use claude      # 用默认服务商启动 Claude Code
ai use codex       # 用默认服务商启动 Codex
```

启动之后就是原生的 Claude Code / Codex 界面，交互方式一个字都不变。区别只在两点：配置是 AxiomRuntime 临时注入的，用量在后台被记下来了。

到这里就算装完了。

### 2.2 装完之后先熟悉这几条命令

```bash
ai                 # 不带参数：交互式菜单，列出所有操作，不用记命令
ai status          # 联网刷一遍所有 Provider 的健康度，看用量
ai provider list   # 只看配置，不联网
ai doctor          # 出问题先跑这个，默认不消耗 token
ai help            # 完整命令手册
ai last            # 沿用上次的工具、服务商和模型
```

如果记不住命令，直接敲 `ai` 就行——它会列出所有能做的事让你选。

加第二个、第三个 Provider：

```bash
ai add                                              # 交互式，推荐
ai provider add 我的站 https://example.com sk-xxx    # 一行搞定
```

添加时自动完成一整串动作：写入配置 → 设 `mode: auto` → 分配下一个可用优先级 → 测连通性 → 探测模型 → 设默认模型。

指定 Provider 和模型启动：

```bash
ai use claude 我的站                    # 指定服务商
ai use claude 我的站 claude-opus-4-6    # 指定服务商 + 模型
ai use codex 我的站 gpt-5.5
```

参数是位置式的：`ai use <工具> [provider] [模型]`，后两个省略就用默认值。

### 2.3 第一次可能遇到的几个问题

| 现象 | 原因 | 怎么办 |
|---|---|---|
| npm 报 `EBADENGINE` | Node 版本低于 22.19 | 先升 Node，再重装。别忽略这个警告 |
| `ai` 命令找不到 | npm 全局 bin 不在 `PATH` 里 | `npm bin -g` 看路径，加到 `PATH` |
| 敲 `ai` 跑的不是这个工具 | 命令名撞了 | `which -a ai` 看有几个，调整 `PATH` 顺序 |
| 上游报 `model_not_found` | 模型名不对 | 跑 `ai status` 刷新模型缓存，从探测结果里选 |
| 连不上 Provider | 网络或 Base URL 写错 | `ai status` 看健康度，`ai doctor` 查配置 |
| 不确定哪里坏了 | —— | `ai doctor`。它检查十几项，默认不消耗 token、不读你的项目源码 |

### 2.4 先回答一个必然被问到的问题：和 cc-switch 什么关系？

这个领域已经有成熟工具了，最有代表性的是 **cc-switch**。如果你在用它，那么下面这段值得看，因为功能重叠比你想象的多，我不打算含糊过去。

先说清楚 cc-switch 已经做了什么。它是一个 Tauri 桌面应用，支持八个客户端（Claude Code、Claude Desktop、Codex、Gemini CLI、Grok Build、OpenCode、OpenClaw、Hermes），内置 50+ provider 预设，有系统托盘一键切换、统一的 MCP / Prompts / Skills 管理、会话浏览、云同步、Deep Link 导入。而且它也有本地代理、自动故障转移、熔断器、provider 健康监控和用量仪表盘。

所以本文第三节里讲的两层降级、熔断器、用量统计，**这些不是差异化**。说它们是，就是在骗你。

真正的区别只有四条。

#### 第一，形态不同：桌面 GUI vs 命令行进程

cc-switch 是一个需要图形界面的桌面应用。AxiomRuntime 是一条命令。

这个差别在下面这些场景里是决定性的：SSH 到远程开发机、跑在容器或 CI 里、无头服务器、纯键盘工作流。

反过来，如果你就在本机图形环境下工作、喜欢点界面、需要托盘快速切换，cc-switch 的形态明显更舒服。

#### 第二，配置的施加方式不同，这是真正的架构分歧

cc-switch 的机制是**写入 live 配置文件**——切换 provider 时把凭证写进 `~/.claude/settings.json`、`~/.codex/auth.json`，编辑时再从这些文件回填。它的 FAQ 里明确说了，系统会始终保留一个"正在激活中"的配置，因为全删了对应的 CLI 就没法用了。

AxiomRuntime 是**每次调用临时注入**——生成临时 settings 文件用 `--settings` 传给这一个子进程，或者用 `-c` 覆盖只对这次生效，进程结束就没了。用户的配置文件全程零改动。

这两种做法各有代价，不是单方面的优劣：

| | cc-switch（写 live 文件） | AxiomRuntime（临时注入） |
|---|---|---|
| 直接敲 `claude` 时 | 切换后的 provider 依然生效 | 走用户原本的配置，不受影响 |
| 用户配置文件 | 被工具持有和改写 | 一个字节都不动 |
| 卸载之后 | 最后写入的配置留在那里 | 无痕，没有东西需要清理 |
| 覆盖范围 | 所有启动方式都生效 | 只对经过 `ai use` 的启动生效 |

看清楚第四行——**这是 cc-switch 那套做法的真实优势**：它的切换是全局的，你用任何方式启动 CLI 都生效。AxiomRuntime 换来的是配置文件的纯净和无痕卸载，代价是必须经过它启动才有效。

选哪个取决于你的偏好：想要一个全局开关，选写 live 文件；想要一个不留痕迹的启动器，选临时注入。我选后者的理由在 3.4 节。

#### 第三，每个终端窗口都是一个独立个体

这是临时注入换来的、最实用的一个能力。

前面那张表只讲了"改不改用户文件"，但临时注入还有一个更大的推论，值得单独拎出来讲：**因为配置是注入给某一个子进程的，所以进程之间天然隔离。**

这意味着你可以同时开一排终端窗口，每个窗口跑不同的 provider、不同的模型、不同的项目，互不干扰：

```bash
# 窗口 1：主力 provider，默认模型，写业务代码
ai use claude

# 窗口 2：另一家 provider 的另一个模型，同时跑
ai use claude backup claude-opus-4-6

# 窗口 3：Codex 跑测试
ai use codex fenno

# 窗口 4：便宜的模型批量处理杂活
ai use claude cheap claude-haiku-4-5
```

四个窗口同时在跑，四套不同的配置，零冲突。关掉任意一个，其他三个不受影响。

这个能力不是功能，是架构的必然结果。任何"写 live 配置文件"的方案在结构上都做不到——因为 `~/.claude/settings.json` 只有一份，全局只能有一个"当前激活的 provider"。cc-switch 的 FAQ 里那句"系统会始终保留一个正在激活中的配置"，说的就是这个约束。它不是实现上的偷懒，是把状态放在全局单例文件里的必然后果。

反过来说，AxiomRuntime 里"当前用哪个 provider"这个状态**不存在于任何全局位置**，它只存在于每个正在运行的子进程里。所以并发数量没有上限，也没有互斥。

实际用起来，这个差别比想象的大：

- **对比测试**：同一个任务，两个窗口用两家 provider 同时跑，直接看谁的结果好、谁更快。不用来回切。
- **成本分层**：重要的活给贵模型，杂活给便宜模型，同时进行。不是"这一小时用贵的、下一小时用便宜的"，而是真正并行。
- **故障隔离**：一家 provider 挂了，只影响用它的那个窗口。其他窗口连感知都没有。
- **多项目并行**：每个项目一个窗口，各自绑定自己合适的模型。

如果你习惯同时开五六个终端，这一条大概是全文对你最有价值的部分。

#### 第四，也是最实质的区别：目标不同

cc-switch 的定位是**配置控制面板**——它把"管好各个工具的配置"这件事做到很全。这是个清晰且有价值的定位，而且在覆盖广度上它做得比 AxiomRuntime 好得多。

AxiomRuntime 的定位是**运行环境**。差别在于它自己执行任务，而不只是配置执行任务的工具。这一条推导出三样 cc-switch 没有、也不该有（因为不在它的定位里）的东西。

**（一）Telegram Bot：一个完整的远程执行入口，不是通知插件。**

需要强调这不是"任务完成了给你推条消息"。是手机上发一句话，Claude Code 或 Codex 在你的机器上真的跑起来，结果和文件改动发回手机。

它是一个和 CLI 平级的接入面，具备的能力包括：

- **实时进度**：一条消息自己在变——现在什么阶段、在调什么工具、回答预览。
- **多 Bot 隔离**：`ai telegram add ops`，每个 bot 有独立的配置、工作目录、日志、会话数据库。可以按项目开好几个，互不干扰。
- **手机上管 provider**：`/provider` 直接增删改查、测连通性、发现模型。不用回到电脑前。
- **`/terminal`**：直接在工作目录跑命令。
- **文件和图片**：一次最多 8 个文件，图片单文件 10MB，直接扔给它看。
- **上下文和固定**：自动保留最近 12 轮，`/pin` 固定最多 3 条关键对话。
- **独立的安全边界**：即使权限模式是 `full-auto`，高风险命令在 Telegram 侧仍强制点确认。这条不能被权限模式绕过——远程入口的风险模型和坐在电脑前不一样。

这就是第一节"痛点三"的答案。一个配置管理工具在架构上无法提供这个——因为它不执行任务，没有可以远程触发的东西。

**（二）CLI 本身是可扩展的能力面，不是几个固定命令。**

CLI 不是"切 provider"一个功能加几个附属命令，它是一组围绕运行环境的能力，而且是按注册表组织的（加命令 = 注册一个，不是改一个大 switch）：

| 命令 | 干什么 |
|---|---|
| `ai use` | 启动工具，带路由和降级 |
| `ai status` | 真实发请求刷健康度，看用量 |
| `ai doctor` | 十几项自检 + 安全的自动修复 |
| `ai provider` | provider 增删改查 |
| `ai session` | 会话记录 |
| `ai log` | 结构化日志（脱敏后） |
| `ai memory` | 记忆管理 |
| `ai context` | 上下文 |
| `ai report` | 用量报表 |
| `ai telegram` | Bot 全生命周期管理 |
| `ai set` | 持久化配置（和 `ai use` 的临时注入区分开） |

`ai doctor` 值得单说：它默认不消耗 token、不读你的项目源码，检查配置完整性、Node 版本、原生依赖、两个 CLI 在不在、provider 连通性、模型探测、默认模型是否存在。能重建的东西自动重建（缺的目录、损坏的缓存先备份再重建），不能重建的只报告——`providers.json` 无效时绝不自动覆盖，因为那里面是你的凭证。

这个边界是有意的：**自动修复的前提是"修错了也不会丢东西"。**

**（三）真正的理由：它会往哪长。**

前面两条已经能用了。但这个项目做下去的理由是第五节那两件事——让运行环境**跨会话积累能力**：

- **记忆**：不用每开一个新会话就重新交代"这个项目用 pnpm 不用 npm""那个 legacy 目录别动"。而且是能看、能改、能删、能钉住的，不是背后偷偷塞。
- **技能沉淀**：同一套流程重复到第五次，它自己开口问要不要存成一个技能，下次一句话触发。

这两件事对配置管理工具来说是无意义的——它不参与执行，没有可以积累的东西。对运行环境来说，这是核心：**每一次交互，都让 Runtime 更有能力。**

这部分现在还没做完，第五节会老实交代做到哪一步了、缺什么。但它是"Runtime"这个名字的由来，也是为什么这不是一个换皮的 provider 切换器。

#### 所以要不要换？我的建议是不必二选一

如果你的需求就是"在多个 provider 和多个客户端之间管配置"，cc-switch 更成熟、覆盖更广、有 GUI，继续用它。

如果你需要在无图形界面的环境里工作、同时开多个窗口跑不同 provider、不希望任何工具持有你的配置文件，或者想从手机上执行任务，那 AxiomRuntime 补的是这几块。

两者的自有存储位置也完全不冲突（`~/.cc-switch/` 和 `~/.ai-gateway/`）。AxiomRuntime 的日常执行命令 `ai use` 不写 live 配置；只有你明确执行 `ai set codex` 时，才会持久修改 Codex 配置。你仍然可以用 cc-switch 管日常配置，用 `ai use` 起并发窗口和手机远程；如果两边都修改 Codex 的持久配置，则以最后一次操作为准。

## 三、核心功能

### 3.1 Provider 管理与优先级

配置的核心就是加几个 provider，每个给一个 level：

```bash
ai provider add 51talk https://example.com sk-xxx
ai provider list
```

每个 provider 有六个字段：名字、`baseUrl`、`apiKey`、模式、优先级、默认模型。

`level 1` 是默认，挂了往下走。这个设计简单到没什么可讲的，但它是后面所有降级逻辑的基础。

添加 provider 时会自动做四件事：测连通性、探测可用模型、设默认模型、分配下一个可用 level。你不用手动填模型名——填错了反而会导致上游报 `model_not_found`。

### 3.2 两层降级机制

`ai status` 会真的发请求刷一遍所有 provider 的健康度，然后你直接 `ai use claude`，它会跳过挂掉的那家。

看起来简单，但这里面是两层完全不同的机制。

**第一层：启动前筛选。**

健康检查已经知道某家是 502，所以它根本不会被列进候选列表。三种情况会被跳过：

- 熔断器打开（这家最近连续失败太多次）
- 健康状态是 `error`
- 这家没有和当前工具兼容的模型

第三条容易被忽略但很重要：Claude Code 只能用带 `claude` 的模型，Codex 能用 `gpt`、`codex`、`grok`、`o` 系列。一家 provider 可能是活的，但它没有你要的那类模型——这种情况也得跳过，而不是让它跑起来再失败。

**第二层：跑起来之后挂了再换。**

如果一家健康检查是通的，但真跑的时候子进程非零退出，它会打出 `Provider xxx unavailable, fallback to yyy`，然后接着试下一家。

**为什么需要两层？**

因为"看起来能不能用"和"实际跑得起来吗"是两件事。

健康检查是轻量的——它只发一个 `GET /v1/models`，不消耗 token，不做真实推理。这意味着有一整类问题它检测不到：模型配额用完了、这个具体模型下线了、上游对长上下文有额外限制。

"健康检查过了但真实推理失败"在实际使用中相当常见，所以运行时降级是必需的，不是冗余。

这两层的行为也不同——第一层是静默跳过，第二层会明确告诉你发生了降级。知道这个区别，遇到时就不会觉得行为不一致。

### 3.3 熔断器：不让一个坏 provider 反复浪费时间

光有降级不够。如果一家 provider 挂了，但每次执行都还是先试它一遍再降级，那你每次都要多等一次超时。

所以健康状态不只是"好/坏"两个值，而是一个带记忆的机制：

- 每个 provider 有一个 0 到 100 的健康分，初始 50
- 成功一次 +25，失败一次 −35
- 连续失败 3 次，熔断器打开，接下来 10 分钟直接跳过这家
- 10 分钟后进入半开状态，会再给一次机会

失败惩罚重于成功奖励这个不对称是有意的：一个刚从故障恢复的 provider，不应该因为一次成功就立刻回到满分被当成首选。它得连续成功几次才能爬回来。

这是熔断器模式的常规做法，没什么创新，但对实际体验影响很大——它把"provider 挂了"从一个**每次都要付出代价**的问题，变成了一个**只付出前三次代价**的问题。

### 3.4 一条关键设计取舍：默认执行不碰用户的配置文件

最直接的实现方式是直接改 `~/.claude/settings.json`，把 baseUrl 和 key 写进去。一行代码搞定，立刻跑通。

但这条路有两个问题：

第一，那是用户自己的配置文件。往里面写东西等于污染他的环境。他自己的配置和工具写的混在一起，出问题时分不清是谁干的。

第二，更严重的——用户没法不用这个工具了。直接敲 `claude`，不经过网关，配置还是被改过的状态。一个"可选的便利工具"就变成了"必须依赖的中间层"。

所以实际实现是这样：

- **Claude Code**：每次启动生成一个临时 settings 文件，用 `--settings` 参数传进去，进程结束就删掉。`~/.claude/settings.json` 一个字都不动。
- **Codex**：用 `-c model_provider=...` 只对这一次子进程生效。全局 `auth.json` 和 `config.toml` 保持原样。

这样你想绕过它直接敲 `claude` 或 `codex`，行为完全不变。这里说的是日常执行命令 `ai use`；后面要讲的 `ai set codex` 是用户明确选择的持久配置操作，两者的边界不同。

这是整个项目最重要的一条设计原则：

> **一个管配置的工具，不应该让你没法不用它。**

这句话是有工程后果的。为了做到这一点，付出的成本是：每次启动要生成和清理临时文件、要读取用户原有配置再合并、要处理两个 CLI 完全不同的注入机制。代码量至少多了三倍。

换来的是**可退出性**。用户任何时候可以不用它，不需要清理任何东西。

顺便说一个相关的坑。Codex 的 provider 配置里有个 `requires_openai_auth` 开关，看名字像是该加的。但它会导致 Codex 把"是否已认证"判定成"`auth.json` 文件在不在"，完全不看 `OPENAI_API_KEY` 环境变量。在没有 `auth.json` 的机器上，就强制弹出 ChatGPT 登录页——用户明明配了自己的 provider，却被要求登录 OpenAI 官方账号。

所以这个开关必须去掉。托管的 provider 靠 `env_key` 完成认证，不依赖 OpenAI 官方身份。

### 3.5 `ai set codex`：让 Codex 桌面端也使用同一个 Provider

`ai use codex` 适合终端：它只影响当前启动的这个 Codex 进程。但 Codex App 不是由这条命令启动的，所以它不会自动继承这些临时参数。

这就是 `ai set codex` 解决的问题：**明确地、一次性地把 Codex 的持久配置切到指定 provider，供 Codex App 和直接执行的 `codex` 使用。**

```bash
ai set codex provider 我的站 gpt-5.6-sol   # 指定 provider 和模型
ai set codex provider 我的站                 # 自动选最新可用 GPT
ai set codex provider                        # 交互选 provider 和模型
ai set codex                                 # 全交互入口
```

Provider 必须已经通过 `ai provider add` 添加。模型也不是凭空猜的：只会从 `ai status` 已探测到的 `gpt-*` 模型中选择。如果没有可用模型，命令会停下来提示你先刷新状态，不会写一份半成品配置。

写入时有几条安全约束：

- `config.toml` 只保存 provider、模型和 Base URL，API Key 只进权限为 `0600` 的 `auth.json`
- Base URL 末尾没有 `/v1` 时自动补上，已经有了就不重复追加
- 原有的 project、MCP、plugin 和 feature 配置都会保留
- 两个文件都采用原子替换，登录取消、认证失败或写入失败都会回滚

如果要切回 ChatGPT 官方账号，用：

```bash
ai set codex chatgpt
```

它会调用 `codex login` 走官方 OAuth。需要注意，切到自定义 provider 会替换当前的 ChatGPT token，以后切回来需要重新登录。

Codex App 走代理时，也不用手改配置：

```bash
ai set codex proxy http://127.0.0.1:7890
ai set codex proxy off
```

输入裸的 `127.0.0.1:7890` 也会自动补成 `http://127.0.0.1:7890`。在 macOS 上，配置成功后会同步当前登录会话的 launchd 环境，再重启 Codex App，让新配置立即生效。

所以这两个命令的分工很清楚：

> **终端里想临时切换、并发跑多个 provider，用 `ai use codex`；想让 Codex App 和直接执行的 `codex` 持续使用某个 provider，用 `ai set codex`。**

### 3.6 用量统计：真实的和估算的要分开

用量记的是 **provider 真实返回的 usage**，不是本地推算的。两条链路的采集方式不一样：

- **Claude 链路**：Claude Code 的 JSON stream 里直接带 `cost_usd`，读出来就行。
- **Codex 链路**：Codex 不给成本，只在响应里给 token。所以本地起了一个 OpenAI 兼容的代理，透明转发请求，把响应里的 usage 记下来。代理不改 Codex 的请求和响应，Codex 完全不知道自己被代理了。

有些模型只给 token 不给费用，这种才会按你自己配的价格表估算：

```json
{
  "51talk-codex/gpt-5.5": {
    "inputPerMillionUsd": 1,
    "outputPerMillionUsd": 3
  }
}
```

关键是：**估算的和实测的分开标**，不混在一起给你一个假精确的数字。价格表没命中的模型直接显示"额度未知"，而不是瞎猜一个。

这也是个原则问题。可观测性工具最容易犯的错就是给一个看起来精确但实际不可靠的数字，用户信了它做决策，比没有数字更糟。

### 3.7 Telegram：把能力从电脑上解放出来

在手机上发一句话，它在你的机器上执行 Claude Code 或 Codex，把结果和文件改动发回来。

**进度显示这块有个坑。**

最直觉的做法是逐 token 更新，像网页版那样一个字一个字出。但 Telegram 的消息编辑接口有频率限制，会直接 429，而且重试的时候还会导致重复执行。

实际方案是：按完整的 JSON stream event 合并，默认至少 1500 毫秒更新同一条消息。你看到的是一条消息自己在变——现在什么阶段、在调什么工具、回答预览。任务结束时，短结果直接覆盖这条进度消息。

没那么炫，但不会挂。

其他能用的：

- **多 Bot 隔离**：`ai telegram add ops`，每个 bot 有自己的配置、工作目录、日志、会话数据库，互不干扰。适合按项目分开。
- **上下文管理**：自动保留最近 12 轮对话，在 1400 token 预算内从新到旧选。`/pin` 可以固定最多 3 条关键对话，防止被挤出去。
- **文件和图片**：一次最多 8 个文件，文本单文件 2MB，图片单文件 10MB，文本注入总预算 3000 token。
- **`/terminal`**：直接在工作目录跑命令，最长 60 秒。
- **`/provider`**：在手机上管理 provider，增删改查、连通性检查、模型发现都能做。API Key 只显示"已配置"，输入之后 bot 会尽力立刻删掉那条 Telegram 消息。

安全边界这块是硬的。即使权限模式设成 `full-auto`，高风险命令的文本仍然会在 Telegram 侧强制点确认。这条不能被权限模式绕过——因为 Telegram 是个远程入口，风险模型和坐在电脑前不一样。

### 3.8 几条写死的安全约束

有几个约束不给配置项：

**root 用户不能跳过权限检查。** Claude Code 官方禁止 root 使用 `--dangerously-skip-permissions`。如果以 root 身份运行并且请求了自动模式，它会把这次执行约束成默认权限、输出告警、记录下"你要的是什么"和"实际生效的是什么"，并且绝不把那个参数传给 Claude Code。

**凭证类记忆拒绝明文保存。** 记忆系统里有个 `credential` 分类，但它目前直接抛错——因为加密还没做完。宁可拒绝这个功能，也不明文存密码。

**配置文件用临时文件加重命名写入。** 因为 CLI 和 Telegram 可能同时在跑，两个进程同时写一个 JSON 会写坏。加上文件锁，避免并发覆盖。

**日志脱敏。** 启动记录里有 API Key 的指纹（前 8 位加后 6 位加长度），但没有完整 key。Telegram token、代理地址在日志和终端输出里都会脱敏。

### 3.9 诊断与自我修复

```bash
ai doctor
```

默认不消耗 token，不读项目源码。它会检查十几项东西：配置文件完整性、Node 版本、原生依赖、两个 CLI 装了没、provider 连通性、模型探测、默认模型存不存在。

它会做安全的自动修复：缺的目录和状态文件直接创建；损坏的缓存文件先备份成 `*.invalid-<时间戳>` 再重建。

但 `providers.json` 无效的时候只报告问题，绝不自动覆盖——那里面是凭证，重建等于删掉。

自动修复的边界很清楚：**可以重建的东西自动重建，不可重建的东西只报告。**

## 四、技术架构：为什么叫 Runtime 而不叫 Gateway

前面讲的所有功能其实都可以塞进一个"provider 网关"里。但项目名字是 Runtime，这不是起名时的随意选择。

### 4.1 一句话定位

项目文档第一页写的是：

> Runtime 才是产品。Model、Provider、Memory、Agent、Skill、Tool、Workflow 都是可替换的能力模块。
>
> 北极星目标是：**每一次交互，都让 Runtime 更有能力。**

这句话的实际含义是：对话结束时，系统不重置。它应该随着使用变得更强。

想要的演进路径是这样的：

```
个人经验 → 知识 → 技能 → 能力 → 组织智能
```

这个定位决定了很多架构选择。如果目标只是"管好 provider"，那不需要契约层，不需要端口-适配器，不需要把 CLI 和 Telegram 都设计成可替换的适配器。但如果目标是"让能力可以累积和替换"，这些就都是必需的。

### 4.2 三条硬不变量

设计文档里有三条约束，称之为**硬不变量**——违反它们，架构就会退化。

**第一条：契约层零依赖，所有人指向它。**

有一层只放接口和类型定义，不依赖任何模块。其他每一层只 import 这层契约，绝不 import 兄弟模块的具体实现。

这一条单独决定了"低耦合"。实际效果是：可以换掉任何一个模块的实现，只要契约不变，上层零改动。

**第二条：端口-适配器。**

每个能力对外暴露一个接口（端口），具体实现是适配器，启动时注入。换 provider、换存储、换检索后端 = 换适配器，上层不动。

这一条决定了"可插拔"。举个具体例子：Claude Code 和 Codex 在架构上不是两个特殊的硬编码分支，而是两个注册进来的引擎适配器。它们各自声明"我怎么归一化 baseUrl""我怎么构造环境变量""我怎么构造命令行参数"，上层的路由、降级、日志逻辑完全不知道它们的区别。

这也是为什么加第三个 CLI 工具的成本是可控的——只需要写一个新的适配器。

**第三条：发现不等于激活。**

插件靠一个描述符（id、版本、需要的权限、配置 schema、健康检查、生命周期）被发现，由策略引擎决定激活。模型和插件都不能自我激活。

这一条是给未来的自动学习准备的，第五节详细讲。

### 4.3 分层结构

目标架构是十二层（从 0 到 11）。这里只讲和理解产品最相关的部分。

**接入面（Surfaces）**：CLI、Telegram、HTTP API，以及未来的 Web、桌面端、定时任务。它们的职责是把用户意图翻译成一个统一的请求对象，然后就交出去。

这条规则很关键：**接入面是适配器，不是逻辑的拥有者。** Telegram bot 不实现 provider 路由，不实现记忆策略，不实现工具授权。它调用核心 API。

为什么？因为如果每个接入面都自己实现一遍路由逻辑，那有三个接入面就有三套可能不一致的行为。用户在 CLI 里看到的降级规则和在 Telegram 里看到的不一样——这是可观测性和可信度的灾难。

这条已经落地：CLI 和 Telegram 共用同一套 provider 解析、降级、健康度和日志逻辑。

**执行内核（Execution Kernel）**：权限、幂等、重试、取消、隔离。

**传输代理（Transport Proxy）**：所有模型请求只经过一个数据平面。

这条"单一数据平面"是个硬约束。当前实现里那个 OpenAI 兼容的用量代理，目标是**原位演进**成这个统一代理，而不是再起第二个。

为什么强调"不要第二个代理"？因为一旦有两个代理，你立刻会遇到：环境变量回环（A 代理指向 B，B 又指回 A）、重复解析、用量双写（同一次调用被记两遍账）、协议适配器行为漂移。这些问题排查起来极其痛苦，而且是设计层面的问题，不是 bug。

所以文档里明确写了：用量的唯一写入者只有一个组件，记忆增强是同一个数据平面里的扩展，不是第二个代理。

### 4.4 关于"不重复造轮子"的一条明确边界

设计文档里有一条原则，划清了自研和复用的界线：

> 只自研体现产品定位的控制面和权威语义。
>
> 抽取、混合检索、向量索引、时序图、检查点、队列、序列挖掘、策略求值、评测、密码学、遥测——这些优先复用成熟实现，并通过适配器、契约测试和本地降级方案避免厂商锁定。

翻译成人话：

- **要自研的**：什么是权威真相、谁有权激活一个能力、审计怎么做、怎么回滚。这些是产品差异化所在。
- **不自研的**：向量数据库、图数据库、消息队列、加密算法、策略语言。这些是通用问题，已经有比自己做得好得多的实现。

而且文档里加了一条硬规则：**不写 ADR（架构决策记录）证明存在实质性的契约或安全缺口，就不允许重新实现一个通用引擎。**

这条规则的意义是给"我想自己写一个"这种冲动设一个门槛。工程师看到一个通用组件不完全符合需求时，第一反应往往是自己写一个。这条规则强制你先证明"现有的确实不行"，而不是"我觉得自己写更爽"。

### 4.5 具体的技术选型

| 决策 | 方案 | 理由 |
|---|---|---|
| 配置存储 | JSON + 文件锁 | 可手工编辑；原子重命名防并发写坏 |
| Telegram 会话 | SQLite | 需要查询、索引、并发安全 |
| 工具执行 | 子进程 spawn | 终端下继承完整 TTY；Telegram 下捕获 JSON stream |
| 用量采集 | 本地 HTTP 代理 | 透明拦截，不改工具本身 |
| 记忆存储 | 中央 SQLite + scope 逻辑隔离 | 用户画像跨 bot 共享，bot 人设只归当前 bot |

有个细节值得说：**为什么配置用 JSON，会话用 SQLite？**

因为它们的访问模式完全不同。`providers.json` 是给人看和手工编辑的，条目少，全量读写，可读性优先。会话数据要按时间查、按 chat 查、并发写，需要索引和事务。

用一种存储硬扛两种需求，结果就是两边都不好用。所以这里故意分开了：面向人的配置用人能读的格式，面向机器的状态用数据库。

### 4.6 现在的实现边界

这点要特别强调：**上面讲的架构是目标架构，不是当前实现。**

当前实现是 Runtime 的网关基础层。设计文档里专门有一张表，逐项列出"规格里有什么"和"代码里有什么"，差距在哪。比如：

| 规格组件 | 代码现状 |
|---|---|
| 单表记忆 | 已实现 |
| Claim/Evidence 账本 | 未实现 |
| scope 分级 | 只有 2 级（终局是 5 级） |
| 多源召回 + 向量检索 | 未实现，当前是关键词打分 |
| 学习治理器 | 未实现 |
| 统一传输代理 | 未实现 |
| 凭证加密存储 | 未实现，API Key 目前明文存 |

这张表放在文档最显眼的位置，因为**规格和实现的落差如果不显式标注，就会变成谎言。** 过一段时间再读到"Claim/Evidence 账本"这段设计，会以为它已经存在了。

顺便，`providers.json` 里的 API Key 目前是明文的。目标架构要求它变成一个引用，真正的凭证存在专门的凭证库里。这个还没做。所以请务必限制这个文件的权限，绝对不要提交到仓库。这是当前实现的一个真实缺口，不打算把它藏在文档角落里。

## 五、接下来做什么

只讲两件已经定下来在做的事。文档里还有一份从个人工具到组织级能力的完整路线图，但那个太远，讲了也是空的。

### 5.1 记忆：让它记住那些说了二十遍的事

每开一个新会话都要重新交代一遍——

> 这个项目用 pnpm 不用 npm。接口都在某个目录下。那个 legacy 目录别动。提交信息要用中文。

说到第二十遍的时候会有点崩。

目标是让它自己记住。但有两个设计要求：

**第一，分层记。** 不能全糊成一锅：

- 关于用户个人习惯的，跨所有项目共享
- 关于某个项目规矩的，只在这个项目生效
- 临时说的事情，过期就清掉

这个分层现在部分实现了：有全局和 bot 两级 scope，短期记忆默认 72 小时后自动清理。但离目标的分层还差得远。

**第二，也是更重要的：得看得见它记了什么。**

底线是：**能看、能改、能删、能钉住。**

不能是它在背后偷偷往上下文里塞东西，然后你都不知道它为什么突然这么回答。这个原则如果做不到，宁可不上这个功能。

所以设计上有几条硬规则：

- **记忆的真相源是一个只追加的账本。** 事实拆成"可以变的断言"和"不可变的证据"，任何修改都是新增一条记录取代旧的，而不是原地改写。随时可以回溯一条记忆是怎么变成现在这样的。
- **模型只能提出候选。** 要不要激活成"系统认为这是真的"，由确定性的策略决定，不是模型自己说了算。
- **用户画像不是真相源，是从底层断言编译出来的产物。** 底层的事实变了，画像重新编译。这意味着纠正一条底层事实，画像会跟着变，而不是留下两个互相矛盾的版本。
- **不可信来源的内容永远不会自动激活。** 模型摘要、网页内容、工具转述——这些不能被"洗白"成可信的用户事实。

**当前的真实状态：**

- 自动记忆还没有。现在得显式让它记，普通聊天不会自己往里写。
- 只接了 Telegram，终端的 `ai use` 还没接上。
- 检索是关键词匹配，不是语义搜索。问的措辞跟当时记的差太远，它找不到。
- 向量模型的配置已经做完了（可以配 Jina 或任何 OpenAI 兼容的 embedding 服务），但真正的向量入库和召回还没做。

为什么先做配置不做检索？因为要先把检索质量的评测基线建起来。没有基线，改完检索算法根本不知道是变好了还是变差了——只能凭感觉，而在检索这个领域，凭感觉基本等于随机。

### 5.2 技能沉淀：让重复五次的流程变成一个命令

每周都要做同一套操作：拉最新分支、跑测试、看哪个挂了、改、提 PR。流程完全一样，但每次都得重新说一遍。

目标是让它到第五次的时候自己开口：

> 这个流程我见过四次了，要不要存成一个技能？下次一句话就能跑。

但同样，不是它觉得自己学会了就直接用。技能沉淀的链路设计成这样：

1. 只从**验证成功过**的执行记录里挖
2. 相似的操作序列聚类——要求至少出现 3 次，且跨至少 3 次独立执行
3. 把具体值抽象成参数（这次改的是 A 文件，下次可能是 B 文件）
4. 和真实执行记录对齐校验，要求 100% 覆盖——不允许凭空多出一个步骤
5. 回放验证、沙箱验证、影子模式验证
6. 通过了才来问要不要启用

而且：

- 高风险步骤强制确认，不能被自动化绕过
- 环境变了（依赖升级、配置改了）强制重新验证
- 连续失败两次自动标记为废弃，并且**移出候选池**——坏经验不能污染后续的挖掘

最后一条最容易被忽略：一个失败的技能如果留在候选池里，它会污染后面所有的挖掘结果。系统会反复尝试一个已知不工作的模式，而且每次都消耗资源。所以失败必须有明确的退出路径。

技能只是**建议性的**程序记忆。运行时的权限检查独立生效——一个技能说"我要执行这个命令"，不代表它就有权限执行。权限永远由内核判定。

### 5.3 这两件事的共同点

记忆和技能这两件事，本质上是同一个问题的两面：

> 如何让一个系统从使用中学到东西，同时不让它悄悄扩大自己的权限。

这就是第四节那条"发现不等于激活"的实际用途。模型可以**提议**——提议记住一件事，提议沉淀一个技能。但**激活**这个提议、让它真的开始影响后续行为，必须经过确定性的策略判定，或者人的批准。

这是自动学习类系统最容易出问题的地方。一个越用越强的系统很诱人。但一个越用越强、同时越用越不受控的系统，是灾难。

## 六、现在还不能做什么

这节必须写。不写就是广告。

- **`ai web` 是个占位。** 命令在，点了会告诉你没实现。目标是企业控制面——组织和身份管理、策略审批、能力和插件生命周期、记忆治理、执行审计、成本归属。现在一个都没有。
- **记忆只接了 Telegram。** 终端的 `ai use` 还没接上。自动记忆没有。检索是关键词匹配，不是语义搜索。
- **API Key 是明文存的。** 目标架构要求凭证进专门的凭证库、配置里只留引用，这个没做。请自己限制文件权限。
- **没有多租户、没有组织级隔离。** 这是个单机工具。文档里那些组织智能、能力共享、联合身份，全是目标态。
- **统一传输代理没做。** 现在的用量代理只服务 Codex 链路，Claude 链路走的是解析 JSON stream。这两条路径要合并成一个数据平面，还没合。
- **命令名是 `ai`，两个字母，很容易撞名。** 装之前 `which ai` 看一眼。

这些都写在文档里，没藏。设计文档里有一整套机制专门用来标注"规格说有、代码里没有"的差距——包括状态、责任人和退出条件。

这个机制本身比任何单个功能都重要。因为一个项目的文档一旦开始撒谎，它就再也不能作为决策依据了。而对一个要长期维护的项目来说，文档不可信意味着后面会基于错误的认知做架构决策。

## 七、三条贯穿整个项目的原则

### 一、可退出性比功能完整性重要

前面那个"不改 `~/.claude/settings.json`"的取舍，代码量翻了三倍。

换来的是：用户任何时候可以不用这个工具，不需要清理任何东西，不需要恢复任何配置。

任何一个插在别人工作流中间的工具，都应该能被无痛移除。**如果不能，它就不是工具，是绑定。**

### 二、承认边界会提升可信度，不是降低

把未实现的东西写得模糊一点——"演进中"、"规划中"、"逐步接入"——很有诱惑力。

但显式列表更好：规格里有什么，代码里有什么，差在哪。

这么做之后，对项目状态的判断会准确得多。而且当文档说"这个已经实现了"的时候，这句话是有分量的——因为读者知道没实现的东西也会照实说。

**模糊的措辞保护的是写文档的人的面子，损害的是读文档的人的决策质量。**

### 三、架构文档先行，但必须承认它是欠条

分层和不变量这些东西，写在前面比补在后面便宜太多。第四节那三条硬不变量，如果不是一开始就定下来，代码早就变成一坨了——CLI 里塞一点路由逻辑，Telegram 里塞一点，然后两边行为不一致，然后谁都不敢改。

但有个前提：**架构文档写的是欠条，不是成绩。** 写了十二层架构，不代表有十二层架构，代表欠了十二层。

所以那张"规格 vs 实现"的对照表不是可选的补充说明，它是让整套文档保持诚实的必要机制。没有它，文档就从"设计蓝图"退化成"愿望清单"。

## 八、怎么开始用

### 安装

```bash
node --version    # 要 22.19+
which ai          # 检查有没有撞名

npm install --global @offerpilot/axiomruntime
ai --version
ai setup
```

### 日常命令

```bash
ai provider add <名字>   # 加个 provider
ai status                # 看健康度和用量
ai use claude            # 起 Claude Code
ai use codex             # 起 Codex
ai set codex              # 持久配置 Codex App
ai doctor                # 出问题先跑这个
ai help                  # 打开完整命令手册
```

### Telegram

```bash
ai telegram add ops
ai telegram config set token <bot-token> --bot ops
ai telegram config set allowedUserIds <你的 telegram 用户 id> --bot ops
ai telegram start --bot ops
```

默认只有白名单里的用户能访问。这是故意的默认值——一个能在你机器上执行命令的 bot，默认应该是封闭的。要开放给所有人得显式改配置。

如果本机连不上 Telegram，配一个代理地址：

```bash
ai telegram config set proxyUrl http://127.0.0.1:7890 --bot ops
```

注意要带协议头。这是个常见的坑，所以交互式配置的时候会显示完整的示例格式。

## 九、最后

现在它是个管 provider 的开关。但目标不止这个。

最终想要的是一个**用得越久越懂你的运行环境**——它记得你的习惯、记得每个项目的规矩、把重复做过的流程沉淀成能一句话触发的技能。而且这些都是看得见、能改、能撤回的。

记忆和技能这两块都还没做完。做完一个发一个，不攒着一次性放大招。

如果你现在的痛点就是"换中转站要改两个地方"和"不知道钱花在哪"，那它现在就能解决。如果你期待的是那个会自己学习的运行环境，那还得等。

安装命令在上面。评论区说说你现在最烦哪一步——按这个排优先级，不是客套。
