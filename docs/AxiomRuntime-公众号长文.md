# 我用一年时间，给 Claude Code 和 Codex 造了一个统一的运行环境

> 这篇文章记录 AxiomRuntime 这个项目：它从一次二十分钟的翻车开始，最后变成了一套一万七千行代码、十一万字设计文档的东西。我会讲清楚它解决什么问题、怎么解决的、哪些地方我一开始做错了又改回来，以及它现在还不能做什么。

---

## 一、起点：一次二十分钟的翻车

去年某天下午，我正在改一个 bug，用的中转站突然 502。

那会儿我手上同时开着两个 AI 编程工具：Claude Code 和 Codex。要切到备用中转站，我得做两件完全不同的事——

Claude Code 认环境变量，我得去改 `ANTHROPIC_BASE_URL` 和 `ANTHROPIC_API_KEY`。

Codex 不认环境变量，它认自己的配置文件，我得去动 `config.toml` 里的 `model_provider`，还得改 `auth.json` 里的凭证。

两套配置，零交集。改完之后我发现 Codex 还是在往老地址发请求，又排查了十几分钟，最后发现是全局 `auth.json` 里的 key 优先级更高，把我刚才改的覆盖掉了。

二十分钟没了。

那天晚上我开始写这个东西。最初的目标特别朴素：**我想要一个开关，让我换中转站只改一个地方。**

一年后，它变成了一万七千多行 TypeScript、九十九个源文件、一万一千行设计文档的项目，一百次提交。名字叫 AxiomRuntime。

这篇文章讲清楚这中间发生了什么。

---

## 二、三个痛点，其实是三个层次的问题

回头看，我遇到的不是一个问题，是三个。它们的严重程度递增。

### 痛点一：配置分散，切换成本高

这是最表层的。两个 CLI 工具的配置机制没有任何交集：一个吃环境变量，一个吃 TOML 加 JSON。你想在多个中转站之间切换，就得记住两套完全不同的操作。

手动改的问题不只是慢，是**容易改一半忘一半**。改了 Claude 忘了 Codex，然后花二十分钟排查为什么行为不一致。

更麻烦的是，当你有三四个 provider 备用的时候，这个成本是乘法而不是加法：`provider 数量 × CLI 数量`。

### 痛点二：不知道钱花在哪

中转站基本不给账单细节。本地也没有任何汇总。

我的真实状态是：月底看余额突然少一大截，但完全不知道是哪个模型、哪个项目、哪次操作吃掉的。想优化都不知道从哪下手。

这是个很典型的**可观测性缺失**问题——不是功能不够，是你看不见系统在干什么。

### 痛点三：人不在电脑前就干不了活

这个是后来才意识到的，但它是我最后决定认真做这个项目的原因。

很多时候我知道要改什么，就一句话的事——改个配置、加个字段、跑一下测试看哪里挂了。但人在外面，只能等回去。

这不是效率问题，这是**能力的可达性问题**。一个只能在特定物理位置使用的能力，实际价值会打折很多。

前两个痛点解决的是"用得顺不顺"，第三个解决的是"用不用得上"。

## 三、它是什么

先把最实用的信息说清楚。

```bash
npm install --global @offerpilot/axiomruntime
ai setup
```

三个名字不一样，这点容易搞混：

| | 名字 |
|---|---|
| 项目名 | AxiomRuntime |
| npm 包名 | `@offerpilot/axiomruntime` |
| 装完的命令 | `ai` |

也支持 Homebrew：

```bash
brew tap linlangli/axiom https://gitlab.com/linlangli/axiom.git
brew install linlangli/axiom/axiomruntime
```

两个前提得先说：

**一，需要 Node.js 22.19 或更高。** Node 20 跑不了。如果 npm 报 `EBADENGINE`，别当普通警告忽略——那个状态下装出来的 CLI 是有问题的，先升 Node。

**二，它不装 Claude Code，也不装 Codex，不替你出 token。** 它只管理你已经有的这些。`ai setup` 会检查这两个 CLI 在不在，缺了会问你要不要装，但装的还是官方的包。

它的定位可以用一句话说：

> **一个统一的入口，管理你在多个 API provider 之间使用 Claude Code 和 Codex 的整个过程——包括路由、降级、用量、会话、诊断，以及从手机上远程执行。**

## 四、核心功能：一个一个说

### 4.1 Provider 管理与优先级

配置的核心就是加几个 provider，每个给一个 `level`：

```bash
ai provider add 51talk https://example.com sk-xxx
ai provider list
```

每个 provider 有六个字段：名字、baseUrl、apiKey、模式、优先级、默认模型。

`level 1` 是默认。挂了往下走。这个设计简单到没什么可讲的，但它是后面所有降级逻辑的基础。

添加 provider 的时候会自动做四件事：测连通性、探测可用模型、设默认模型、分配下一个可用 level。你不用手动填模型名——填错了反而会导致上游报 `model_not_found`。

### 4.2 两层降级，这是我最想讲的部分

`ai status` 会真的发请求刷一遍所有 provider 的健康度，然后你直接 `ai use claude`，它会跳过挂掉的那家。

看起来很简单，但这里面其实是**两层完全不同的机制**。我一开始只做了第一层，后来发现不够，才补了第二层。

**第一层：启动前筛选。**

健康检查已经知道某家是 502，所以它根本不会被列进候选列表。三种情况会被跳过：

- 熔断器打开（这家最近连续失败太多次）
- 健康状态是 error
- 这家没有和当前工具兼容的模型

第三条容易被忽略但很重要：Claude Code 只能用带 `claude` 的模型，Codex 能用 `gpt`、`codex`、`grok`、`o` 系列。一家 provider 可能是活的，但它没有你要的那类模型——这种情况也得跳过，而不是让它跑起来再失败。

**第二层：跑起来之后挂了再换。**

如果一家健康检查是通的，但真跑的时候子进程非零退出，它会打出 `Provider xxx unavailable, fallback to yyy`，然后接着试下一家。

**为什么需要两层？**

因为"看起来能不能用"和"实际跑得起来吗"是两件事。

健康检查是轻量的——它只发一个 `GET /v1/models`，不消耗 token，不做真实推理。这意味着有一整类问题它检测不到：模型配额用完了、这个具体模型下线了、上游对长上下文有额外限制。

我一开始以为健康检查够了。上线之后发现"健康检查过了但真实推理失败"的情况相当常见，才补了运行时降级。

这两层是分开的，行为也不同——第一层是静默跳过，第二层会明确告诉你发生了降级。知道这个区别，以后遇到就不会觉得行为不一致。

### 4.3 熔断器：不让一个坏 provider 反复浪费你时间

光有降级不够。如果一家 provider 挂了，但每次执行都还是先试它一遍再降级，那你每次都要多等一次超时。

所以健康状态不只是"好/坏"两个值，而是一个带记忆的机制：

- 每个 provider 有一个 0 到 100 的健康分，初始 50
- 成功一次 +25，失败一次 -35（失败的惩罚比成功的奖励重，这是故意的）
- 连续失败 3 次，熔断器打开，接下来 10 分钟直接跳过这家
- 10 分钟后进入半开状态，会再给一次机会

**失败惩罚重于成功奖励**这个不对称是有意的：一个刚从故障恢复的 provider，不应该因为一次成功就立刻回到满分被当成首选。它得连续成功几次才能爬回来。

这个设计我参考的是熔断器模式的常规做法，没什么创新，但对实际体验的影响很大——它把"provider 挂了"从一个每次都要付出代价的问题，变成了一个只付出前三次代价的问题。

### 4.4 一个我一开始做错的设计

这是全文我最想讲的一段。

**最早我的做法是：直接改 `~/.claude/settings.json`**，把 baseUrl 和 key 写进去。

跑通了，很爽，一行代码搞定。

但很快发现两个问题：

**第一，这是用户自己的配置文件。** 我往里面写东西，等于污染了他的环境。他自己的配置和我写的混在一起，出问题的时候分不清是谁干的。

**第二，更严重的——你没法不用我这个工具了。** 你直接敲 `claude`，不经过我，配置还是被我改过的状态。我把一个"可选的便利工具"变成了"必须依赖的中间层"。

后来改成这样：

- **Claude Code**：每次启动生成一个**临时** settings 文件，用 `--settings` 参数传进去，进程结束就删掉。`~/.claude/settings.json` 一个字都不动。
- **Codex**：用 `-c model_provider=...` 只对这一次子进程生效。全局 `auth.json` 和 `config.toml` 保持原样。

这样你想绕过它直接敲 `claude` 或 `codex`，行为完全不变。

我认为这个取舍是这个项目最重要的一条设计原则：

> **一个管配置的工具，不应该让你没法不用它。**

这句话听起来像句漂亮话，但它是有工程后果的。为了做到这一点，我付出的成本是：每次启动要生成和清理临时文件、要读取用户原有配置再合并、要处理两个 CLI 完全不同的注入机制。代码量至少多了三倍。

但换来的是**可退出性**。用户任何时候可以不用它，不需要清理任何东西。

顺便说一个相关的坑。Codex 的 provider 配置里有个 `requires_openai_auth` 开关，我一开始加上了，看名字觉得应该加。结果它导致 Codex 把"是否已认证"判定成"`auth.json` 文件在不在"，完全不看 `OPENAI_API_KEY` 环境变量。在没有 `auth.json` 的机器上，就强制弹出 ChatGPT 登录页——用户明明配了自己的 provider，却被要求登录 OpenAI 官方账号。

后来把这个开关去掉了。我们托管的 provider 靠 `env_key` 完成认证，不依赖 OpenAI 官方身份。

### 4.5 用量统计：真实的和估算的要分开

用量是顺手做的，但后来变成我最常看的功能。

它记的是 **provider 真实返回的** usage，不是我自己算的。两条链路的采集方式不一样：

**Claude 链路**：Claude Code 的 JSON stream 里直接带 `cost_usd`，读出来就行。

**Codex 链路**：Codex 不给成本，只在响应里给 token。所以本地起了一个 OpenAI 兼容的代理，透明转发请求，把响应里的 usage 记下来。**代理不改 Codex 的请求和响应**，Codex 完全不知道自己被代理了。

有些模型只给 token 不给费用，这种才会按你自己配的价格表估算：

```json
{
  "51talk-codex/gpt-5.5": {
    "inputPerMillionUsd": 1,
    "outputPerMillionUsd": 3
  }
}
```

关键是：**估算的和实测的分开标，不混在一起给你一个假精确的数字。** 价格表没命中的模型直接显示"额度未知"，而不是瞎猜一个。

这也是个原则问题。可观测性工具最容易犯的错就是给一个看起来精确但实际不可靠的数字，用户信了它做决策，比没有数字更糟。

### 4.6 Telegram：把能力从电脑上解放出来

这是我自己用得最多的部分。

在手机上发一句话，它在你的机器上执行 Claude Code 或 Codex，把结果和文件改动发回来。

**进度显示这块我踩过坑。**

最早我想做成逐 token 更新，像网页版那样一个字一个字出。结果 Telegram 的消息编辑接口有频率限制，直接 429，而且重试的时候还会导致重复执行。

后来改成：按完整的 JSON stream event 合并，默认至少 1500 毫秒更新**同一条**消息。你看到的是一条消息自己在变——现在什么阶段、在调什么工具、回答预览。任务结束时，短结果直接覆盖这条进度消息。

没那么炫，但不会挂。这个取舍我觉得值。

其他能用的：

- **多 Bot 隔离**：`ai telegram add ops`，每个 bot 有自己的配置、工作目录、日志、会话数据库，互不干扰。我自己开了几个对应不同项目。
- **上下文管理**：自动保留最近 12 轮对话，在 1400 token 预算内从新到旧选。`/pin` 可以固定最多 3 条关键对话，防止被挤出去。
- **文件和图片**：一次最多 8 个文件，文本单文件 2MB，图片单文件 10MB，文本注入总预算 3000 token。
- **`/terminal`**：直接在工作目录跑命令，最长 60 秒。
- **`/provider`**：在手机上管理 provider，增删改查、连通性检查、模型发现都能做。API Key 只显示"已配置"，输入之后 bot 会尽力立刻删掉那条 Telegram 消息。

**安全边界这块是硬的。** 即使你把权限模式设成 `full-auto`，高风险命令的文本仍然会在 Telegram 侧强制你点确认。这条不能被权限模式绕过——因为 Telegram 是个远程入口，风险模型和你坐在电脑前不一样。

### 4.7 一些安全上的硬约束

有几个约束是写死的，不给配置项：

**root 用户不能跳过权限检查。** Claude Code 官方禁止 root 使用 `--dangerously-skip-permissions`。如果你以 root 身份运行并且请求了自动模式，它会把这次执行约束成默认权限、输出告警、记录下"你要的是什么"和"实际生效的是什么"，并且**绝不**把那个参数传给 Claude Code。

**凭证类记忆拒绝明文保存。** 记忆系统里有个 `credential` 分类，但它目前直接抛错——因为加密还没做完。宁可拒绝这个功能，也不明文存密码。

**配置文件用临时文件加重命名写入。** 因为 CLI 和 Telegram 可能同时在跑，两个进程同时写一个 JSON 会写坏。加上文件锁，避免并发覆盖。

**日志脱敏。** 启动记录里有 API Key 的指纹（前 8 位加后 6 位加长度），但没有完整 key。Telegram token、代理地址在日志和终端输出里都会脱敏。

### 4.8 诊断与自我修复

```bash
ai doctor
```

默认不消耗 token，不读你的项目源码。它会检查十几项东西：配置文件完整性、Node 版本、原生依赖、两个 CLI 装了没、provider 连通性、模型探测、默认模型存不存在。

它会做**安全的自动修复**：缺的目录和状态文件直接创建；损坏的缓存文件先备份成 `*.invalid-<时间戳>` 再重建。

但 `providers.json` 无效的时候只报告问题，**绝不自动覆盖**——那里面是你的凭证，重建等于删掉。

自动修复的边界很清楚：可以重建的东西自动重建，不可重建的东西只报告。

## 五、技术架构：为什么叫 Runtime 而不叫 Gateway

到这里，前面讲的所有功能其实都可以塞进一个"provider 网关"里。但项目名字是 Runtime，这不是起名时的随意选择。

### 5.1 一句话定位

项目文档第一页写的是：

> **Runtime 才是产品。Model、Provider、Memory、Agent、Skill、Tool、Workflow 都是可替换的能力模块。**

北极星目标是：**每一次交互，都让 Runtime 更有能力。**

这句话的实际含义是：对话结束时，系统**不重置**。它应该随着使用变得更强。

我想要的演进路径是这样的：

```
个人经验 → 知识 → 技能 → 能力 → 组织智能
```

这个定位决定了很多架构选择。如果目标只是"管好 provider"，那我不需要契约层，不需要端口-适配器，不需要把 CLI 和 Telegram 都设计成可替换的适配器。但如果目标是"让能力可以累积和替换"，这些就都是必需的。

### 5.2 三条硬不变量

设计文档里有三条约束，我称之为硬不变量——违反它们，架构就会退化。

**第一条：契约层零依赖，所有人指向它。**

有一层只放接口和类型定义，不依赖任何模块。其他每一层只 import 这层契约，**绝不 import 兄弟模块的具体实现**。

这一条单独决定了"低耦合"。它的实际效果是：你可以换掉任何一个模块的实现，只要契约不变，上层零改动。

**第二条：端口-适配器。**

每个能力对外暴露一个接口（端口），具体实现是适配器，启动时注入。

换 provider、换存储、换检索后端 = 换适配器，上层不动。

这一条决定了"可插拔"。举个具体例子：Claude Code 和 Codex 在架构上不是两个特殊的硬编码分支，而是两个注册进来的引擎适配器。它们各自声明"我怎么归一化 baseUrl""我怎么构造环境变量""我怎么构造命令行参数"，上层的路由、降级、日志逻辑完全不知道它们的区别。

这也是为什么加第三个 CLI 工具的成本是可控的——你只需要写一个新的适配器。

**第三条：发现不等于激活。**

插件靠一个描述符（id、版本、需要的权限、配置 schema、健康检查、生命周期）被**发现**，由策略引擎决定**激活**。

模型和插件都不能自我激活。

这一条是给未来的自动学习准备的，我在第六节详细讲。

### 5.3 分层结构

目标架构是十二层（从 0 到 11）。这里只讲和理解产品最相关的部分。

**接入面（Surfaces）**：CLI、Telegram、HTTP API，以及未来的 Web、桌面端、定时任务。

它们的职责是**把用户意图翻译成一个统一的请求对象**，然后就交出去。

这条规则很关键：**接入面是适配器，不是逻辑的拥有者。** Telegram bot 不实现 provider 路由，不实现记忆策略，不实现工具授权。它调用核心 API。

为什么？因为如果每个接入面都自己实现一遍路由逻辑，那你有三个接入面就有三套可能不一致的行为。用户在 CLI 里看到的降级规则和在 Telegram 里看到的不一样——这是可观测性和可信度的灾难。

目前这条已经落地：CLI 和 Telegram 共用同一套 provider 解析、降级、健康度和日志逻辑。

**执行内核（Execution Kernel）**：权限、幂等、重试、取消、隔离。

**传输代理（Transport Proxy）**：所有模型请求只经过**一个**数据平面。

这条"单一数据平面"是个硬约束。当前实现里那个 OpenAI 兼容的用量代理，目标是原位演进成这个统一代理，而不是再起第二个。

为什么强调"不要第二个代理"？因为一旦有两个代理，你立刻会遇到：环境变量回环（A 代理指向 B，B 又指回 A）、重复解析、用量双写（同一次调用被记两遍账）、协议适配器行为漂移。这些问题排查起来极其痛苦，而且是设计层面的问题，不是 bug。

所以文档里明确写了：用量的唯一写入者只有一个组件，记忆增强是同一个数据平面里的扩展，不是第二个代理。

### 5.4 关于"不重复造轮子"的一条明确边界

设计文档里有一条我认为很重要的原则，它划清了自研和复用的界线：

> **只自研体现产品定位的控制面和权威语义。**
>
> 抽取、混合检索、向量索引、时序图、检查点、队列、序列挖掘、策略求值、评测、密码学、遥测——这些优先复用成熟实现，并通过适配器、契约测试和本地降级方案避免厂商锁定。

翻译成人话：

- **我要自研的**：什么是权威真相、谁有权激活一个能力、审计怎么做、怎么回滚。这些是产品差异化所在。
- **我不自研的**：向量数据库、图数据库、消息队列、加密算法、策略语言。这些是通用问题，已经有比我做得好得多的实现。

而且文档里加了一条硬规则：**不写 ADR（架构决策记录）证明存在实质性的契约或安全缺口，就不允许重新实现一个通用引擎。**

这条规则的意义是给"我想自己写一个"这种冲动设一个门槛。工程师看到一个通用组件不完全符合需求时，第一反应往往是自己写一个。这条规则强制你先证明"现有的确实不行"，而不是"我觉得自己写更爽"。

### 5.5 具体的技术选型

| 决策 | 方案 | 理由 |
|---|---|---|
| 配置存储 | JSON + 文件锁 | 可手工编辑；原子重命名防并发写坏 |
| Telegram 会话 | SQLite | 需要查询、索引、并发安全 |
| 工具执行 | 子进程 spawn | 终端下继承完整 TTY；Telegram 下捕获 JSON stream |
| 用量采集 | 本地 HTTP 代理 | 透明拦截，不改工具本身 |
| 记忆存储 | 中央 SQLite + scope 逻辑隔离 | 用户画像跨 bot 共享，bot 人设只归当前 bot |

有个细节值得说：**为什么配置用 JSON，会话用 SQLite？**

因为它们的访问模式完全不同。`providers.json` 是给人看和手工编辑的，条目少，全量读写，可读性优先。会话数据要按时间查、按 chat 查、并发写，需要索引和事务。

用一种存储硬扛两种需求，结果就是两边都不好用。所以这里故意分开了：面向人的配置用人能读的格式，面向机器的状态用数据库。

### 5.6 现在的实现边界

这是我要特别强调的一点：**上面讲的架构是目标架构，不是当前实现。**

当前实现是 Runtime 的网关基础层。设计文档里专门有一张表，逐项列出"规格里有什么"和"代码里有什么"，差距在哪。比如：

| 规格组件 | 代码现状 |
|---|---|
| 单表记忆 | 已实现 |
| Claim/Evidence 账本 | 未实现 |
| scope 分级 | 只有 2 级（终局是 5 级） |
| 多源召回 + 向量检索 | 未实现，当前是关键词打分 |
| 学习治理器 | 未实现 |
| 统一传输代理 | 未实现 |
| 凭证加密存储 | 未实现，API Key 目前明文存 |

我把这张表放在文档最显眼的位置，因为**规格和实现的落差如果不显式标注，就会变成谎言**。半年后有人（包括我自己）读到"Claim/Evidence 账本"这段设计，会以为它已经存在了。

顺便，`providers.json` 里的 API Key 目前是明文的。目标架构要求它变成一个引用，真正的凭证存在专门的凭证库里。这个还没做。**所以现在请务必限制这个文件的权限，绝对不要提交到仓库。** 这是当前实现的一个真实缺口，我不打算把它藏在文档角落里。

## 六、接下来做什么

我只讲两件已经定下来在做的事。文档里还有一份从个人工具到组织级能力的完整路线图，但那个太远，讲了也是空的。

### 6.1 记忆：让它记住那些我说了二十遍的事

你们有没有这种感觉：每开一个新会话都要重新交代一遍——

这个项目用 pnpm 不用 npm。接口都在某个目录下。那个 legacy 目录别动。提交信息要用中文。

说到第二十遍的时候会有点崩。

我想让它自己记住。但有两个设计要求：

**第一，分层记。**

不能全糊成一锅：

- 关于我这个人的习惯，跨所有项目共享
- 关于某个项目的规矩，只在这个项目生效
- 这次临时说的事情，过期就清掉

这个分层现在部分实现了：有全局和 bot 两级 scope，短期记忆默认 72 小时后自动清理。但离目标的分层还差得远。

**第二，也是更重要的：你得看得见它记了什么。**

这是我的底线：**能看、能改、能删、能钉住。**

不是它在背后偷偷往上下文里塞东西，然后你都不知道它为什么突然这么回答。

这个原则如果做不到，我宁可不上这个功能。

所以设计上有几条硬规则：

- 记忆的真相源是一个**只追加**的账本。事实拆成"可以变的断言"和"不可变的证据"，任何修改都是新增一条记录取代旧的，而不是原地改写。**你随时可以回溯一条记忆是怎么变成现在这样的。**
- 模型只能**提出候选**。要不要激活成"系统认为这是真的"，由确定性的策略决定，不是模型自己说了算。
- 用户画像不是真相源，是从底层断言**编译出来的产物**。底层的事实变了，画像重新编译。这意味着你纠正一条底层事实，画像会跟着变，而不是留下两个互相矛盾的版本。
- 不可信来源的内容**永远不会自动激活**。模型摘要、网页内容、工具转述——这些不能被"洗白"成可信的用户事实。

**当前的真实状态，我说清楚：**

- 自动记忆**还没有**。现在得你显式让它记，普通聊天不会自己往里写。
- 只接了 Telegram，终端的 `ai use` 还没接上。
- 检索是关键词匹配，不是语义搜索。你问的措辞跟当时记的差太远，它找不到。
- 向量模型的配置已经做完了（可以配 Jina 或任何 OpenAI 兼容的 embedding 服务），但真正的向量入库和召回还没做。

为什么先做配置不做检索？因为我想先把检索质量的评测基线建起来。**没有基线，你改完检索算法根本不知道是变好了还是变差了**——只能凭感觉，而在检索这个领域，凭感觉基本等于随机。

### 6.2 技能沉淀：让重复五次的流程变成一个命令

第二件事。

你每周都要做同一套操作：拉最新分支、跑测试、看哪个挂了、改、提 PR。流程完全一样，但每次都得重新跟它说一遍。

我想让它到第五次的时候自己开口：

> 这个流程我见过四次了，要不要存成一个技能？下次一句话就能跑。

但同样，**不是它觉得自己学会了就直接用。**

技能沉淀的链路设计成这样：

1. 只从**验证成功过**的执行记录里挖
2. 相似的操作序列聚类——要求至少出现 3 次，且跨至少 3 次独立执行
3. 把具体值抽象成参数（这次改的是 A 文件，下次可能是 B 文件）
4. 和真实执行记录对齐校验，**要求 100% 覆盖**——不允许凭空多出一个步骤
5. 回放验证、沙箱验证、影子模式验证
6. 通过了才来问你要不要启用

而且：

- 高风险步骤强制确认，不能被自动化绕过
- 环境变了（依赖升级、配置改了）强制重新验证
- 连续失败两次自动标记为废弃，**并且移出候选池**——坏经验不能污染后续的挖掘

最后一条是我觉得最容易被忽略的：**一个失败的技能如果留在候选池里，它会污染后面所有的挖掘结果。** 系统会反复尝试一个已知不работ的模式，而且每次都消耗资源。所以失败必须有明确的退出路径。

**技能只是建议性的程序记忆。** 运行时的权限检查独立生效——一个技能说"我要执行这个命令"，不代表它就有权限执行。权限永远由内核判定。

### 6.3 这两件事的共同点

写到这里我发现，记忆和技能这两件事，本质上是同一个问题的两面：

**如何让一个系统从使用中学到东西，同时不让它悄悄扩大自己的权限。**

这就是第五节那条"发现不等于激活"的实际用途。模型可以提议——提议记住一件事，提议沉淀一个技能。但激活这个提议、让它真的开始影响后续行为，必须经过确定性的策略判定，或者人的批准。

我认为这是自动学习类系统最容易出问题的地方，也是我在设计上花最多时间的地方。

一个越用越强的系统很诱人。但一个越用越强、同时越用越不受控的系统，是灾难。

## 七、现在还不能做什么

这节必须写。不写就是广告。

**`ai web` 是个占位。** 命令在，点了会告诉你没实现。目标是企业控制面——组织和身份管理、策略审批、能力和插件生命周期、记忆治理、执行审计、成本归属。现在一个都没有。

**记忆只接了 Telegram。** 终端的 `ai use` 还没接上。自动记忆没有。检索是关键词匹配，不是语义搜索。

**API Key 是明文存的。** 目标架构要求凭证进专门的凭证库、配置里只留引用，这个没做。请自己限制文件权限。

**没有多租户、没有组织级隔离。** 这是个单机工具。文档里那些组织智能、能力共享、联合身份，全是目标态。

**统一传输代理没做。** 现在的用量代理只服务 Codex 链路，Claude 链路走的是解析 JSON stream。这两条路径要合并成一个数据平面，还没合。

**命令名是 `ai`，两个字母，很容易撞名。** 装之前 `which ai` 看一眼。

这些我都写在文档里，没藏。设计文档一万一千行，里面有一整套机制专门用来标注"规格说有、代码里没有"的差距——包括状态、责任人和退出条件。

我认为这个机制本身比任何单个功能都重要。因为**一个项目的文档一旦开始撒谎，它就再也不能作为决策依据了**。而对一个我打算做好几年的项目来说，文档不可信意味着我半年后会基于错误的认知做架构决策。

## 八、一年下来我学到的三件事

### 一、可退出性比功能完整性重要

前面讲的那个"不改 `~/.claude/settings.json`"的取舍，代码量翻了三倍。

但它换来的是：用户任何时候可以不用这个工具，不需要清理任何东西，不需要恢复任何配置。

我现在的判断是：**任何一个插在别人工作流中间的工具，都应该能被无痛移除。** 如果不能，它就不是工具，是绑定。

### 二、承认边界会提升可信度，不是降低

刚开始写文档的时候，我倾向于把未实现的东西写得模糊一点——"演进中"、"规划中"、"逐步接入"。

后来改成显式列表：规格里有什么，代码里有什么，差在哪。

这么做之后，我自己对项目状态的判断准确多了。而且当我说"这个已经实现了"的时候，这句话是有分量的——因为读者知道我没实现的东西也会照实说。

**模糊的措辞保护的是写文档的人的面子，损害的是读文档的人的决策质量。**

### 三、架构文档比代码先行，但必须承认它是欠条

这个项目一万七千行代码，配了一万一千行文档。比例高得有点离谱。

我一开始怀疑这是过度设计。现在的判断是：分层和不变量这些东西，写在前面比补在后面便宜太多了。第五节那三条硬不变量，如果不是一开始就定下来，现在的代码早就变成一坨了——CLI 里塞一点路由逻辑，Telegram 里塞一点，然后两边行为不一致，然后谁都不敢改。

但有个前提：**架构文档写的是欠条，不是成绩。** 你写了十二层架构，不代表你有十二层架构，代表你欠了十二层。

所以那张"规格 vs 实现"的对照表不是可选的补充说明，它是让整套文档保持诚实的必要机制。没有它，文档就从"设计蓝图"退化成"愿望清单"。

## 九、怎么开始用

```bash
node --version                                    # 要 22.19+
which ai                                          # 检查有没有撞名
npm install --global @offerpilot/axiomruntime
ai --version
ai setup
```

然后：

```bash
ai provider add <名字> <baseUrl> <apiKey>   # 加个 provider
ai status                                   # 看健康度和用量
ai use claude                               # 起 Claude Code
ai use codex                                # 起 Codex
ai doctor                                   # 出问题先跑这个
ai help                                     # 打开完整命令手册
```

Telegram：

```bash
ai telegram add ops
ai telegram config set token <bot-token> --bot ops
ai telegram config set allowedUserIds <你的 telegram 用户 id> --bot ops
ai telegram start --bot ops
```

**默认只有白名单里的用户能访问。** 这是故意的默认值——一个能在你机器上执行命令的 bot，默认应该是封闭的。要开放给所有人得显式改配置。

如果本机连不上 Telegram，配一个代理地址：

```bash
ai telegram config set proxyUrl http://127.0.0.1:7890 --bot ops
```

注意要带协议头。这个坑我自己踩过，所以交互式配置的时候会显示完整的示例格式。

这个东西现在是个管 provider 的开关。但我想做的不止这个。

我最终想要的是一个**用得越久越懂我的运行环境**——它记得我的习惯、记得每个项目的规矩、把我重复做过的流程沉淀成能一句话触发的技能。而且这些都是我看得见、能改、能撤回的。

记忆和技能这两块都还没做完。我做完一个发一个，不攒着一次性放大招。

如果你现在的痛点就是"换中转站要改两个地方"和"不知道钱花在哪"，那它现在就能解决。如果你期待的是那个会自己学习的运行环境，那还得等。

安装命令在上面。评论区说说你现在最烦哪一步——我按这个排优先级，不是客套。
